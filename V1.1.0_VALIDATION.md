# mddocx v1.1.0 Validation Report

## Release objective

v1.1.0 is an additive **Interactive CLI / Windows UX** release. It keeps the frozen public API compatibility version at `1` and layers `mddocx shell` over the existing compiler/project/QA services. No renderer, parser, AST, OMML, ChartML, project-build, or security-policy implementation was duplicated inside the interactive UI.

## Interactive CLI delivered

- `mddocx shell [WORKSPACE]`
- startup workspace dashboard and numbered main menu
- menu + direct REPL commands
- Markdown/DOCX/data/template file discovery and picker
- guided Markdown → DOCX render wizard
- direct `render FILE.md -o FILE.docx`
- exact-host opt-in for detected HTTPS image resources during the guided wizard
- project `build`, `watch`, `new`, `project`, and bounded `config` workflows
- Markdown `check`
- DOCX `inspect` and accessibility dashboard
- `doctor`, `benchmark`, template/data inspection and system-font browser
- session diagnostics and common diagnostic explanations
- persistent command history/autocomplete with `prompt-toolkit`
- non-TTY redirected-input fallback
- recent render/build history containing paths/settings only
- `open` last/result document through the OS file association
- `cd`, `pwd`, `files`, `menu`, `clear`, categorized `help`, `exit`
- top-level `mddocx recent`, `mddocx open`, `mddocx --version`
- top-level `--open` for single-file rendering and project builds

## Architecture boundary

Validated dependency direction:

```text
Interactive console
       ↓
Existing mddocx public/services layer
       ↓
Markdown parser → canonical AST → normalizer → native DOCX renderer
```

There is no renderer → CLI, parser → CLI, or AST → CLI dependency.

## Security checks

The interactive layer does not weaken existing security rules:

- no generic shell execution command exists;
- Markdown/code blocks are never executed;
- guided remote-resource consent applies only to detected HTTPS image hosts;
- existing private/loopback/link-local/non-global host blocking remains active;
- project/resource path confinement remains active;
- YAML is still handled through safe loading/dumping;
- plugins remain explicit opt-in entry points;
- `open` uses OS file associations rather than a user-supplied shell command.

## Tooling note

`ruff` and `mypy` are not installed in this sandbox. Release validation therefore used Python bytecode compilation, the complete pytest suite, isolated-wheel smoke testing, strict DOCX/accessibility inspection, deterministic rebuild comparison, and rendered-page QA. The repository continues to declare Ruff/mypy in the development extra for normal CI/developer environments.

## Release conclusion
